1. **Создать репозиторий на GitHub**
- На GitHub нажми `New repository`
- Укажи имя (например, `ink-auth`)
- Лучше без `README/.gitignore` на этом этапе (чтобы не было конфликтов при первом пуше)

3. **Инициализировать git и сделать первый коммит** (если ещё не делал)
```bash
git init
git add .
git commit -m "Initial commit"
```

4. **Привязать удалённый репозиторий GitHub**
```bash
git branch -M main
git remote add origin https://github.com/<твой-логин>/<имя-репо>.git
```

5. **Отправить код на GitHub**
```bash
git push -u origin main
```

## Что делает каждая команда

- `git --version`  
  Проверка, что Git установлен и доступен в терминале.

- `git config --global user.name "..."`  
  Устанавливает имя автора коммитов **для всех репозиториев на этом компе**.

- `git config --global user.email "..."`  
  Устанавливает email автора коммитов (тоже глобально).  
  GitHub использует его, чтобы привязать коммиты к аккаунту.

- `git config --global --list`  
  Показать текущие глобальные настройки Git (проверка, что всё сохранилось).

---

- `git init`  
  Превращает текущую папку в git-репозиторий (создает скрытую папку `.git` с историей).

- `git add .`  
  Добавляет все текущие файлы в **staging area** (подготовка к коммиту).  
  Это как “я хочу включить эти изменения в следующий снимок”.

- `git commit -m "Initial commit"`  
  Создает первый коммит — сохранённый снимок проекта с сообщением.

---

- `git branch -M main`  
  Переименовывает (или создает имя) основной ветки в `main`.

- `git remote add origin <URL>`  
  Привязывает локальный репозиторий к удаленному на GitHub.  
  `origin` — просто стандартное имя для “удаленного репо”.

- `git push -u origin main`  
  Отправляет ветку `main` на GitHub.  
  Флаг `-u` запоминает связь: локальная `main` <-> удаленная `origin/main`.  
  После этого можно просто писать `git push` и `git pull` без длинных параметров.

---

## Важные понятия (очень коротко)

- **Working directory** — твои файлы на диске прямо сейчас.
- **Staging area** — “корзина” того, что войдет в следующий коммит (`git add`).
- **Commit** — сохраненный снимок проекта в истории.
- **Remote (`origin`)** — репозиторий на GitHub.
- **Push** — отправить локальные коммиты в удаленный репозиторий.

## Почему так получилось

1. **Чаты не всегда = облако.** Часть истории живёт в локальных данных Cursor. **Logout / очистка данных / другая машина** — и список может не совпасть или пропасть.
2. **Привязка к проекту.** Иногда переписка показывается, когда открыт **тот же workspace** (папка проекта). На Mac нужно открыть **склонированный репозиторий** той же папкой, а не просто пустой Cursor.
3. **Два «аккаунта» без заметной разницы.** Email один, но вход через Google vs GitHub иногда даёт **разные связки** с данными (редко, но бывает). Стоит убедиться, что на Mac ты заходишь **тем же способом**, что и на Windows.

## Что сделать сейчас (по шагам)

1. На Mac открой Cursor и залогинься **тем же способом**, что на Windows (если был GitHub — снова GitHub).
2. **File → Open Folder** и открой папку клонированного проекта (например `ink-auth`), не отдельный файл.
3. Открой панель чата и посмотри **список прошлых чатов** (иконка истории / выпадающий список чатов — зависит от версии UI).
4. В **Settings** поищи по словам `sync`, `chat`, `history` — если есть опции синхронизации, включи и посмотри, меняется ли поведение.

## Честный вывод

Если после выхода из аккаунта история **нигде не появилась**, часто это уже **не восстановить** из интерфейса — клиент мог удалить локальный кэш. Для важных инструкций на будущее лучше дублировать: **копировать в заметки / в README в репо / в gist**.

Если напишешь **версию Cursor на Mac** (About) и **как именно логинился** (Google/GitHub/email), можно сузить причину точнее — но принцип выше обычно верный: **не рассчитывать, что чаты переживут logout и перенос на другой ПК без явной облачной синхронизации.**

## Связи и архитектура

1. **`index.html`** подключает три скрипта **без `type="module"`** — глобальные функции из `utils`/`auth` доступны в `main.js`. Это согласовано с текущей разметкой.

2. **Доска:** `main.js` задаёт `src` iframe на `test.html` с query-параметрами (ББ, board id, readonly). События вроде `fabric-save-request`, `fabric-save-done`, `fabric-exit-request`, `fabric-bookmark-*` — контракт между оболочкой и редактором.

3. **`lion-gate-page`** — изолированный арт/лендинг-кусок; **не интегрирован** в `index.html`. Если цель — единый продукт, нужно явно решить: редирект, ссылка с логина или отдельный деплой.

4. **`scripts/storage.js`** в репозитории **нет** (логика хранения ушла в Fabric/`localStorage` по ключам из `main.js` и `test.html`), хотя **`work-log.md`** ещё упоминает `storage.js` и старый вариант с `type="module"` — имеет смысл поправить журнал при следующем коммите, чтобы не путать.

## Риски и качество

- **Безопасность:** только клиент; пароли в `auth.js` — для прототипа ок, для продакшена нужен backend.  
- **Целостность:** доверие к `postMessage` без жёсткой проверки `origin` (если планируется хостинг не только с `file://`/одного домена — стоит ужесточить).  
- **Поддерживаемость:** весь редактор в одном **`test.html`** — быстро развивается, но тяжело ревьюить; логичный следующий шаг — разбить на модули при стабилизации API.  
- **Репозиторий:** очень тяжёлые PNG (`assets/image.png`, `lion-gate-page/logo-ink.png`) и большие `.md` логи — долгий `git clone`, без LFS/сжатия будет больно.

Как делают профессионально:

- Если это внутренний инструмент и deep-link не важен — часто оставляют как есть (быстрее и проще).

Обычно 2 варианта роутинга:

1. **History API** (`/home`, `/boards`, `/board/5`)

   - требует настройки сервера (fallback всех маршрутов на один входной файл)

2. **Hash routing** (`/#/home`, `/#/boards`)  
   - проще, почти без серверных настроек

Правильная схема:

- ворота остаются отдельной сценой (например `lion-gate-page/index.html`);

- анимация ворот = один этап,
- роутинг приложения = следующий этап.

- если смешать всё в одну страницу и без контроля удалять/перерисовывать DOM, где идёт анимация.
- решается тем, что ворота живут отдельно (как у тебя сейчас) или в отдельном изолированном контейнере.

Итог:  
**роутинг + ворота совместимы**, это нормальная профессиональная практика.

### 3. PostgreSQL на Mac

Установка (пример через Homebrew):

```bash
brew install postgresql@16
brew services start postgresql@16
```

Добавь `postgresql` в PATH, если `psql` не находится (brew подскажет команду `echo 'export PATH=...'`).

Создай пользователя и базу **как ожидает бэкенд** (по умолчанию в коде):

```bash
createuser -s inkauth 2>/dev/null || true
psql postgres -c "ALTER USER inkauth WITH PASSWORD 'inkauth';"
createdb -O inkauth inkauth 2>/dev/null || true
```

Восстановление из дампа (формат **custom**, нужен **`pg_restore`**):

```bash
cd ~/Documents/ink-auth   # корень проекта
pg_restore --clean --if-exists --no-owner --role=inkauth -d inkauth backups/inkauth_latest.dump
```

Если будут ошибки прав — можно так:

```bash
pg_restore --clean --if-exists --no-owner -d inkauth backups/inkauth_latest.dump
```
